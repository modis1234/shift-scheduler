# Android 앱·푸시 알림 기획서

상태: v0.2 구현 인계안(2026-10-20). 사용자 확정: **관리자·직원 모두 대상**, **푸시 알림 포함**, **Android 우선·iOS 후속**, 운영 호스트는 Fly.io 도쿄(`nrt`). 지금은 개발 버전이므로 **새 비용이 없는 PWA·Web Push·TWA APK 직접 설치 검증을 먼저 하고, Google Play 등록과 유료 운영은 후속 단계**로 미룬다.

## 1. 목적과 범위

- 웹 서비스를 다시 만드는 대신 현재 PWA를 Android의 Trusted Web Activity(TWA)로 감싸 먼저 APK로 직접 설치해 검증하고, 후속으로 Google Play에서 설치할 수 있게 한다.
- 로그인한 매장 관리자는 기존 `근무표 만들기·근무표 관리·내 일정`을, 직원은 기존 `/s/<공유 코드>`의 게시 근무표를 같은 앱에서 쓴다.
- 직원에게 새 게시 근무표를 알리고, 관리자에게 본인의 `내 일정`을 미리 알린다.
- IT에 익숙하지 않은 사용자가 브라우저·앱의 차이를 배우지 않아도 같은 용어와 흐름을 쓰게 한다.
- 1단계 범위 밖: Play 등록·프로덕션 배포, 유료 도메인, 상시 실행 푸시 작업자, 네이티브 화면 재작성, 두 개의 Play 앱, 직원 계정·본인 인증, 개인별 근무 시작 알림, 오프라인 근무표 저장, iOS App Store 등록, 결제.

## 2. 현재 상태와 핵심 결정

### 2.1 현재 상태

- 웹 앱은 Fly.io 개발 서버 `https://shift-scheduler-wispy-water-5363.fly.dev`에 배포되며 HTTPS를 쓴다. 현재 머신은 유휴 시 정지하므로 정확한 시각의 리마인더를 보장할 수 없다.
- 관리자는 카카오 로그인 후 `/`에서 세 기능을 사용한다. 직원은 로그인 없이 매장 공유 링크 `/s/<공유 코드>`를 연다.
- 현재 `manifest.webmanifest`의 범위는 `/s/`뿐이고 시작 주소가 없다. 따라서 직원 공유 화면만 설치 대상으로 삼은 기존 베타 상태다.
- 서비스 워커, Web Push 구독, 푸시 발송 작업자와 관련 DB는 아직 없다.
- `내 일정`은 `manager_events`에 영속 저장된다. 일정의 날짜·시각은 현재 시간대 필드 없이 한국 매장 기준으로 해석한다.

### 2.2 추천 구조

1. **앱은 하나**로 만든다. Play 등록·서명·심사·업데이트를 이중으로 운영할 이유가 없고, 같은 사람이 관리자와 직원 화면을 한 기기에서 열 수도 있다.
2. 웹의 설치 범위를 `/`로 넓히고 앱 시작 주소를 `/app`으로 고정한다. `/app`은 관리자 로그인 상태와 마지막 직원 공유 링크를 보고 적절한 화면으로 안내하는 가벼운 진입 화면이다.
3. 표준 **Web Push + VAPID + 서비스 워커**를 사용한다. 제품이 별도 Firebase 프로젝트나 Firebase SDK에 종속되지 않게 한다.
4. 직원 푸시는 **매장·현재 공유 링크**에만 연결하고 직원 이름에는 연결하지 않는다. 이름 선택은 `localStorage` 편의 기능일 뿐 본인 인증이 아니다.
5. 잠금 화면에는 제목·직원 이름·근무 시각·메모를 싣지 않는다. 알림은 앱을 열어 확인하게 하는 일반 문구만 쓴다.
6. 1단계는 현재 `*.fly.dev` HTTPS 주소와 무료 표준 Web Push를 이용해 PWA·푸시 기반 및 Bubblewrap 디버그 APK 직접 설치까지 검증한다. 2단계에서 운영 주소·상시 작업자·Play 계정을 마련해 배포하고, 그 뒤 iOS 홈 화면 PWA의 Web Push를 검증한다.

## 3. 사용자와 권한

| 사용자 | 확인 방법 | 허용 기능 | 허용하지 않음 |
|---|---|---|---|
| 매장 관리자 | 기존 카카오 세션, `store_id` | 앱 진입, 근무표 관리, `내 일정`, 이 기기의 관리자 알림 켜기·끄기 | 다른 매장 구독 조회·변경 |
| 직원 | 유효한 `/s/<공유 코드>` 보유 | 게시 근무표 보기, 이 기기의 해당 매장 게시 알림 켜기·끄기 | 개인별 알림, 관리자 일정, 직원 이름과 구독 연결 |
| 서버 작업자 | 서버 전용 DB·VAPID 비밀 키 | 발송 대상 조회, 알림 발송, 실패 정리 | 사용자 화면 접근 |

- 푸시 권한은 계정 권한이 아니라 **브라우저 프로필·설치 앱·기기별 권한**이다. 같은 사용자가 기기를 바꾸면 새로 켜야 한다.
- 한 기기에서 관리자와 직원 알림을 모두 켤 수 있다. 하나의 Web Push 구독에 여러 알림 대상을 연결한다.
- 직원 공유 코드는 열람 권한이므로 알림 등록 API에도 같은 권한으로 쓴다. 코드가 바뀌면 기존 직원 구독 대상도 즉시 삭제한다.

## 4. 정보 구조와 사용자 흐름

### 4.1 하나의 앱 진입

`/app` 진입 순서는 다음과 같다.

1. 유효한 관리자 세션이 있으면 `/`로 이동한다.
2. 관리자 세션이 없고 이 기기에 마지막으로 연 직원 공유 코드가 있으면 `/s/<공유 코드>`로 이동한다.
3. 둘 다 없으면 역할 선택 화면을 보여 준다.

```
┌ 교대근무 스케줄러 ─────────────────┐
│ 어떤 화면을 열까요?                    │
│                                      │
│ [매장 관리자 로그인]                   │
│ 근무표를 만들고 내 일정을 관리합니다.     │
│                                      │
│ 직원은 매장에서 받은 직원 공유 링크를      │
│ 카카오톡·문자에서 눌러 열어 주세요.         │
└──────────────────────────────────────┘
```

- 공유 코드를 직접 타이핑하게 하지 않는다. 22자 코드는 입력 오류가 잦고 전달 경로가 이미 링크이기 때문이다.
- 마지막 직원 링크가 만료되면 자동 이동을 반복하지 않고 역할 선택으로 돌아와 `직원 공유 링크가 바뀌었습니다. 매장에서 새 링크를 받아 열어 주세요.`를 보여 준다.
- 화면 용어는 UI 가이드대로 `근무표`, `내 일정`, `직원 공유 링크`, `알림`을 쓴다. 사용자 화면에 TWA, PWA, VAPID, 토큰을 쓰지 않는다.

### 4.2 알림 켜기

브라우저의 권한 창을 첫 방문에 바로 띄우지 않는다.

1. 사용자가 맥락이 있는 화면에서 설명을 읽고 명시적으로 버튼을 누른다.
   - 관리자 `내 일정`: `[내 일정 알림 받기]`
   - 직원 게시 근무표: `[새 근무표 알림 받기]`
2. 지원 여부를 확인한다. 미지원이면 권한 창 없이 안내한다.
3. 사용자 클릭 안에서 알림 권한을 요청한다.
4. 허용되면 서비스 워커의 구독 정보를 서버에 저장하고 `이 기기에서 알림을 받습니다.`를 보여 준다.
5. 알림별 설정 화면으로 이동해 종류를 켜거나 끌 수 있다.

권한 상태별 문구:

| 상태 | 화면과 행동 |
|---|---|
| 요청 전 | 알림이 오는 이유 한 문장 + 알림 종류 + `[알림 받기]` |
| 요청 중 | `[알림 켜는 중…]`, 중복 클릭 방지, `aria-busy="true"` |
| 허용 | `이 기기에서 알림을 받습니다.` + `[알림 설정]` |
| 창을 닫음 | `알림을 켜지 않았습니다. 원할 때 다시 눌러 주세요.` |
| 거부 | `알림이 차단되어 있습니다. 휴대폰의 앱 또는 사이트 설정에서 알림을 허용해 주세요.`; 브라우저 권한 창을 다시 띄우지 않음 |
| 미지원 | `이 기기에서는 알림을 사용할 수 없습니다. 최신 Chrome에서 다시 확인해 주세요.` |
| 서버 저장 실패 | `알림을 켜지 못했습니다. 인터넷 연결을 확인한 뒤 다시 시도해 주세요.`; 브라우저 구독만 생겼다면 서버 재등록을 재시도 |

### 4.3 알림 끄기

- `알림 설정`에서 현재 기기의 대상별 스위치를 끈다. 서버의 해당 대상 연결을 삭제한다.
- 마지막 연결까지 삭제하면 브라우저 구독도 해지한다. 다른 관리자·직원 대상이 남아 있으면 브라우저 구독은 유지한다.
- 전체 알림 권한을 OS에서 끈 경우 다음 앱 진입 때 서버 연결을 정리하고 설정 이동 안내를 보여 준다.
- 관리자 로그아웃만으로 관리자 알림을 임의 해제하지 않는다. 알림은 기기별 명시적 동의이고 다시 로그인하지 않아도 예정 리마인더를 받을 수 있다. 공용 기기 사용자는 로그아웃 전에 `[이 기기의 관리자 알림 끄기]`를 선택할 수 있게 한다.

## 5. 알림 종류·대상·문구

알림 본문은 잠금 화면에서 보일 수 있으므로 개인 일정 제목, 메모, 직원 이름, 근무조와 시각을 포함하지 않는다.

| 종류 | 대상·발송 조건 | 제목 | 본문 | 누르면 |
|---|---|---|---|---|
| 새 근무표 게시 | 현재 공유 링크의 직원 구독. 새 기간 게시 또는 같은 기간 게시본 교체 후 | `{매장명} 새 근무표` | `{11월 1일~11월 30일} 근무표가 게시되었습니다. 앱에서 확인해 주세요.` | 현재 `/s/<코드>` |
| 게시 근무표 변경 | 현재 공유 링크의 직원 구독. 게시 취소로 기존 공개 내용이 사라짐 | `{매장명} 근무표 변경` | `게시된 근무표가 변경되었습니다. 앱에서 확인해 주세요.` | 현재 `/s/<코드>` |
| 오늘의 내 일정 | 관리자 구독. 하루 종일 일정이 있는 날 09:00 | `오늘의 내 일정` | `오늘 확인할 일정이 있습니다. 앱에서 확인해 주세요.` | `/?tab=my-calendar&date=YYYY-MM-DD` |
| 곧 시작할 내 일정 | 관리자 구독. 시각이 있는 일정 시작 30분 전 | `내 일정 알림` | `30분 뒤 일정이 있습니다. 앱에서 확인해 주세요.` | 같은 날짜의 `내 일정` |

- 서비스 기준 시간대는 v1에서 `Asia/Seoul`로 고정한다. 해외 매장 지원 시 매장별 IANA 시간대 필드를 별도 기획한다.
- 하루 종일 일정이 여러 개여도 09:00에 한 번만 보낸다. 시각 일정은 일정마다 한 번 보낸다.
- 생성·수정 시 이미 알림 시각이 지난 일정은 즉시 보내지 않는다. 다음 예약분부터 적용한다.
- 일정이 수정·삭제되면 아직 발송하지 않은 예약은 새 값으로 다시 계산하거나 취소한다.
- 발송 실패 때문에 근무표 게시·일정 저장을 실패 처리하지 않는다. 사용자 데이터 저장을 먼저 확정하고 알림은 별도 작업자가 처리한다.
- 직원 개인별 근무 시작 알림은 직원 계정 또는 본인 확인이 생긴 뒤 재기획한다.

## 6. 화면 목록과 상태

### 6.1 앱 시작 `/app`

구성: 앱 아이콘, 앱 이름, `어떤 화면을 열까요?`, `[매장 관리자 로그인]`, 직원 링크 안내, 개인정보 처리방침 링크.

| 상태 | 표시 |
|---|---|
| 확인 중 | 로고 아래 `열 화면을 확인하는 중…`, `aria-live="polite"` |
| 관리자 세션 | `/`로 이동 |
| 저장한 직원 링크 | `/s/<코드>`로 이동 |
| 아무 정보 없음 | 역할 선택 목업 |
| 저장한 링크 만료 | 만료 안내 + 역할 선택 |
| 오프라인 | `인터넷에 연결되지 않았습니다. 연결한 뒤 다시 시도해 주세요.` + `[다시 시도]` |

### 6.2 관리자 `내 일정`의 알림 카드

```
┌ 내 일정 알림 ─────────────────────────────┐
│ 이 기기에서 일정이 있는 날과 시작 전에 알려 드립니다. │
│  [✓] 오전 9시 오늘 일정      [✓] 시작 30분 전       │
│                         [시험 알림] [알림 끄기] │
└──────────────────────────────────────────┘
```

- `내 일정` 설명 아래, 달력 위에 둔다. 권한 요청 전에는 종류 스위치 대신 설명과 `[내 일정 알림 받기]`를 둔다.
- 정상, 요청 중, 거부, 미지원, 저장 오류 상태는 4.2절 문구를 쓴다.
- `[시험 알림]`은 등록된 현재 기기에만 보내며 1분에 한 번으로 제한한다. 성공은 `시험 알림을 보냈습니다.`, 실패는 `시험 알림을 보내지 못했습니다. 잠시 뒤 다시 시도해 주세요.`

### 6.3 직원 근무표의 알림 카드

```
┌ 새 근무표 알림 ───────────────────────────┐
│ 새 근무표가 게시되면 이 기기에 알려 드립니다.      │
│                       [새 근무표 알림 받기] │
└──────────────────────────────────────────┘
```

- 유효한 직원 공유 링크 화면에서만 보인다. 이름 선택 여부와 무관하게 켤 수 있다.
- 허용 후에는 `이 기기에서 새 근무표 알림을 받습니다.` + `[시험 알림] [알림 끄기]`를 보인다.
- 링크가 바뀐 뒤 이전 화면을 열면 구독은 복구하지 않고 기존 링크 만료 안내만 보여 준다.

### 6.4 Android 설치·Play 화면

- 웹에서 설치를 강요하는 전면 팝업은 쓰지 않는다. 1단계 개발 APK는 테스터에게만 파일과 설치 방법을 전달하며 일반 사용자 화면에는 `[APK 설치]`를 노출하지 않는다. Play 배포 전에는 브라우저 메뉴의 홈 화면 설치를 지원하고, 배포 뒤 로그인·직원 화면의 작은 안내에서 `[Google Play에서 설치]`를 제공한다.
- Play 스토어 문구 추천:
  - 앱 이름: `교대근무 스케줄러`
  - 짧은 설명: `근무표를 만들고 공유하며 내 일정을 알림으로 확인하세요.`
- 스토어 스크린샷은 관리자 근무표 만들기, 근무표 관리, 내 일정, 직원 근무표를 사용하되 실제 직원 이름·매장명·공유 코드를 넣지 않는다.

## 7. 모바일·키보드·접근성

- 최소 터치 영역 44×44px, 주 버튼 높이 40px 이상, 페이지 전체 가로 스크롤 없음. UI 가이드의 색 대비·포커스 링·다크 모드·`prefers-reduced-motion`을 따른다.
- 알림 스위치는 `<input type="checkbox">` 또는 동일한 키보드·스크린리더 동작을 갖고, 라벨에 알림 시각과 대상을 포함한다.
- 권한 상태와 시험 발송 결과는 `aria-live="polite"`, 오류는 `role="alert"`로 읽는다. 권한 창이 닫히면 포커스를 누른 버튼 또는 상태 안내로 되돌린다.
- Android 뒤로가기는 TWA를 즉시 종료하지 않고 웹 탐색 기록을 따른다. 외부 카카오 로그인·개인정보 처리방침은 브라우저 전환 여부를 실제 기기에서 확인한다.
- 알림을 누르면 이미 열린 앱 창을 앞으로 가져오고 해당 경로로 이동한다. 새 창을 중복해서 만들지 않는다.
- 서비스 워커는 앱 셸과 오프라인 안내만 캐시한다. 직원 근무표·관리자 일정·API 응답은 기존 `no-store`를 지키고 캐시에 넣지 않는다.

## 8. 데이터 영속화와 최소 계약

푸시 알림은 앱을 닫은 뒤에도 보내야 하므로 **서버 영속화가 필수**다. 구독 endpoint와 키는 메시지를 보낼 수 있는 민감한 capability 정보로 취급한다.

### 8.1 DB

```text
push_subscriptions
- id UUID PK
- endpoint TEXT UNIQUE NOT NULL
- p256dh TEXT NOT NULL
- auth TEXT NOT NULL
- expires_at TIMESTAMPTZ NULL
- last_seen_at, last_success_at TIMESTAMPTZ NULL
- failure_count INTEGER NOT NULL DEFAULT 0
- created_at, updated_at TIMESTAMPTZ NOT NULL

push_topics
- subscription_id UUID FK push_subscriptions ON DELETE CASCADE
- store_id TEXT FK stores ON DELETE CASCADE
- audience TEXT CHECK IN ('manager', 'staff')
- share_code_hash TEXT NULL
- schedule_published BOOLEAN NOT NULL DEFAULT false
- manager_all_day BOOLEAN NOT NULL DEFAULT false
- manager_timed BOOLEAN NOT NULL DEFAULT false
- created_at, updated_at TIMESTAMPTZ NOT NULL
- PK (subscription_id, store_id, audience)

notification_outbox
- id UUID PK
- kind TEXT NOT NULL
- store_id TEXT FK stores ON DELETE CASCADE
- subject_id TEXT NULL
- scheduled_for TIMESTAMPTZ NOT NULL
- payload JSON NOT NULL              # 민감한 제목·메모·직원 정보 금지
- state TEXT CHECK IN ('pending', 'processing', 'sent', 'failed', 'cancelled')
- attempt_count INTEGER NOT NULL DEFAULT 0
- dedupe_key TEXT UNIQUE NOT NULL
- available_at, created_at, sent_at TIMESTAMPTZ NULL
```

- `push_topics.share_code_hash`는 직원일 때만 필수이며 현재 공유 코드의 SHA-256을 저장한다. 관리자는 `NULL`이다.
- 한 브라우저 구독을 관리자와 직원 대상이 함께 참조할 수 있어야 하므로 구독과 대상을 분리한다.
- 모든 표에 RLS를 켜고 브라우저에서 Supabase Data API로 직접 접근하지 않는다. 기존처럼 서버 DB 연결만 사용한다.
- VAPID 개인 키는 DB·클라이언트·로그에 두지 않고 Fly secret으로만 둔다. 환경 변수 최소 계약은 `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`이다.

### 8.2 API

| 요청 | 권한·동작 | 주요 응답 |
|---|---|---|
| `GET /api/push/public-key` | 공개. VAPID 공개 키만 반환 | `200 { publicKey }` |
| `PUT /api/push/subscription` | 관리자 로그인. 구독 upsert 후 해당 `store_id`의 manager topic 연결 | `200 { enabled, preferences }` |
| `DELETE /api/push/subscription` | 관리자 로그인. 현재 endpoint의 manager topic 삭제 | `204` |
| `POST /api/push/test` | 관리자 로그인, 등록된 현재 endpoint, 분당 1회 | `202` |
| `PUT /api/s/<code>/push-subscription` | 유효한 공유 코드. 구독 upsert 후 staff topic 연결 | `200 { enabled: true }` |
| `DELETE /api/s/<code>/push-subscription` | 유효한 공유 코드. 해당 staff topic 삭제 | `204` |
| `POST /api/s/<code>/push-test` | 유효한 공유 코드, 등록된 현재 endpoint, 분당 1회 | `202` |

공통 요청의 `subscription`은 브라우저 `PushSubscription.toJSON()`의 `endpoint`, `expirationTime`, `keys.p256dh`, `keys.auth`만 받는다. 서버는 URL 형식, 키 길이, 요청 크기를 검증한다. 오류는 endpoint·키를 응답이나 로그에 출력하지 않는다.

- 관리자 API는 `Cache-Control: no-store`, CSRF 방어를 적용한다.
- 직원 API는 기존 공유 화면과 같이 `no-store`, `noindex`, `no-referrer`를 유지하고 IP+코드 기준 속도 제한을 둔다.
- `POST /api/share-link`로 코드를 새로 만들 때 같은 트랜잭션에서 해당 매장의 staff topic을 모두 삭제한다.
- 마지막 topic을 삭제한 구독 행은 삭제한다. 404/410 Push Service 응답도 즉시 구독과 topic을 삭제한다.

### 8.3 발송 작업자

- 근무표 게시·게시 취소 트랜잭션은 중복 방지 키와 함께 outbox를 기록한다. 예: `schedule:<id>:published:<updated_at>`.
- 관리자 일정 리마인더는 별도의 상시 실행 작업자가 `Asia/Seoul` 기준으로 due 이벤트를 조회해 outbox를 만든다. 동일 `(일정 id, 일정 updated_at, 알림 종류, 예정 시각)`은 한 번만 만든다.
- 작업자는 DB 잠금 또는 원자적 상태 전환으로 한 건을 한 작업자만 처리한다. 일시 실패는 지수 간격으로 최대 3회 재시도하고, 영구 실패는 정리한다.
- 1단계에는 동일 명령을 개발 PC에서 수동 실행하고 시험 시각을 주입해 발송·중복 방지만 검증한다. 정확한 실제 시각의 상시 리마인더는 완료 기준에 넣지 않는다.
- 현재 유휴 시 정지하는 Fly HTTP 머신에 리마인더를 맡기지 않는다. 2단계 운영 전에는 별도 `push-worker` process group을 상시 실행하거나 동일 수준의 예약 실행 서비스를 선택한다.

## 9. 개인정보·보안·보관 정책

1. 직원 이름을 구독과 저장·추론하지 않는다. 직원 대상은 `store_id + 현재 공유 코드 해시`뿐이다.
2. 잠금 화면 payload에는 매장명, 기간, 일반 안내와 이동 경로만 넣는다. 개인 일정 제목·메모·직원 근무 내용은 넣지 않는다.
3. 구독 endpoint, `p256dh`, `auth`는 비밀 값으로 마스킹하고 애플리케이션 로그·분석 도구·오류 추적 본문에 남기지 않는다.
4. 전 구간 HTTPS만 허용한다. 운영 주소 변경 시 Digital Asset Links와 설치 앱의 신뢰가 함께 바뀌므로 주소를 출시 전에 고정한다.
5. 직원 구독은 알림 끄기, 공유 링크 교체, 매장 삭제, Push Service 404/410, 마지막 성공·사용 후 180일 경과 중 먼저 오는 때 삭제한다.
6. 관리자 구독은 알림 끄기, 매장 삭제, Push Service 404/410, 마지막 앱 접속 후 180일 경과 중 먼저 오는 때 삭제한다. 만료 7일 전 앱에서 계속 받을지 다시 확인할 수 있다.
7. 알림 발송 로그에는 알림 종류·시각·성공/실패 코드·구독 내부 ID만 30일 보관한다. endpoint와 알림 본문은 기록하지 않는다.
8. 앱 내와 Play 등록 정보에 개인정보 처리방침 URL을 제공하고 푸시 구독 정보의 목적, 보관, 철회 방법을 추가한다. Play Data safety 답변은 실제 코드·SDK와 일치시킨다.
9. 관리자 계정 삭제 흐름은 관련 푸시 구독·대상·예약 알림도 연쇄 삭제한다. Play의 계정 삭제 안내와 웹 경로를 함께 제출한다.

## 10. PWA·TWA·Play 출시 계약

### 10.1 웹/PWA

- manifest 권장값: `id: "/"`, `start_url: "/app"`, `scope: "/"`, `display: "standalone"`, 앱 이름 `교대근무 스케줄러`.
- 192×192와 512×512 PNG 아이콘을 제공하고 512 아이콘에는 `purpose: "any maskable"` 변형을 추가한다. 현재 128 아이콘은 보조로 유지할 수 있다.
- 루트 레이아웃이 manifest와 `theme-color`, Apple touch icon을 제공해 관리자·직원 경로 모두 같은 앱 범위에 들어가게 한다.
- 서비스 워커의 범위는 `/`다. 새 버전 활성화 중 작성 중인 폼을 강제로 새로고침하지 않고, `새 버전을 사용할 수 있습니다. 작업을 저장한 뒤 새로고침해 주세요.`를 보여 준다.
- 기존 `/s/` 범위로 설치한 직원 베타 앱의 자동 전환은 보장하지 않는다. QA에서 기존 설치본 업데이트를 확인하고 불가능하면 `기존 홈 화면 아이콘을 지우고 Play 앱을 설치해 주세요.`를 한 번 안내한다.

### 10.2 TWA

- Bubblewrap으로 별도 `android/` 프로젝트를 생성·버전 관리한다. 웹이 기능의 원본이며 네이티브 화면을 중복 구현하지 않는다.
- `twa-manifest.json`의 `enableNotifications`를 `true`로 두어 알림 위임을 켜고 알림용 단색 아이콘을 제공한다. Android 13 이상에서는 웹 알림 권한과 앱의 `POST_NOTIFICATIONS` 상태를 함께 확인한다.
- 1단계는 개발용 application ID와 디버그 서명으로 APK를 만들고 테스터 기기에 직접 설치한다. 현재 `*.fly.dev` origin의 `/.well-known/assetlinks.json`에 디버그 인증서 SHA-256 지문을 등록한다. 출처를 알 수 없는 앱 설치 허용은 해당 테스트가 끝나면 다시 끄도록 안내한다.
- 프로덕션 패키지 이름은 2단계 출시 전에 고정한다. 추천: 소유한 역도메인 기반 `kr.<소유도메인>.shiftscheduler`; 임시 `fly.dev` 이름을 프로덕션 패키지에 넣지 않는다.
- 2단계 운영 origin의 `/.well-known/assetlinks.json`에는 패키지 이름과 Play App Signing 인증서 SHA-256 지문을 등록한다. 모든 assetlinks 응답은 리다이렉트 없이 제공한다.
- Digital Asset Links 검증이 실패해 주소창이 있는 Custom Tab으로 열리면 TWA 완료로 보지 않는다.
- 개발 APK도 현재 시점의 Play 신규 앱 기준과 같은 `targetSdkVersion 36`(Android 16)을 사용해 나중의 차이를 줄인다. 정책은 출시 직전에 다시 확인한다.

### 10.3 Play 제출(2단계 후속)

- Play App Signing을 사용하고 업로드 키는 비밀 저장소에 백업한다. 버전마다 `versionCode`를 올린다.
- 등록 항목: 앱 이름·설명·아이콘·스크린샷·지원 연락처·개인정보 처리방침·Data safety·광고 여부·콘텐츠 등급·대상 연령.
- 심사 접근 안내에 관리자 카카오 로그인 방법과 직원용 유효한 검수 링크를 제공한다. 검수 링크에는 실제 직원 데이터가 아닌 전용 샘플 매장·근무표를 쓴다.
- 2023-11-13 이후 만든 개인 개발자 계정은 프로덕션 신청 전 최소 12명이 14일 연속 참여하는 비공개 테스트가 필요할 수 있으므로 계정 상태를 먼저 확인한다.
- 내부 테스트 → 비공개 테스트 → 프로덕션 순서로 배포한다. 실기기에서 로그인, 딥 링크, 푸시, 뒤로가기, 공유 링크 재발급을 확인한다.

## 11. 단계별 구현과 완료 기준

### 1단계 — 비용 없는 개발 검증(PWA·Web Push·TWA APK)

1. `/app`이 관리자 세션·마지막 직원 링크·빈 상태에 따라 4.1절대로 이동하거나 안내한다.
2. manifest 범위가 `/`이고 관리자·직원 양쪽 경로가 같은 설치 앱에서 열린다.
3. 사용자의 버튼 클릭 전에는 권한 창이 뜨지 않으며 허용·닫음·거부·미지원·서버 오류 상태 문구가 정확하다.
4. 같은 기기의 구독 하나에 관리자와 직원 topic을 함께 연결하고 한쪽을 꺼도 다른 쪽이 유지된다.
5. 직원 구독 DB·API·로그 어디에도 선택한 직원 이름이 남지 않는다.
6. 공유 링크를 새로 만들면 이전 링크의 직원 topic이 삭제되고 이전 링크로 알림을 보낼 수 없다.
7. 서비스 워커는 API와 일정 데이터를 캐시하지 않으며 오프라인에는 일반 안내만 보인다.
8. DB RLS, VAPID secret, 입력 검증, 속도 제한, endpoint 마스킹을 확인한다.
9. 근무표 게시·교체·게시 취소 때 실제 직원 기기에 알림이 한 번만 오며 발송 실패가 게시 저장을 되돌리지 않는다.
10. 로컬에서 작업자를 수동 실행하고 시험 시각을 주입하면 관리자 하루 종일·시각 일정 알림, 수정·삭제·중복 방지가 동작한다. 작업자가 꺼진 동안 정시 발송은 보장하지 않는다는 개발 한계를 기록한다.
11. 현재 `*.fly.dev`와 디버그 인증서를 연결한 APK를 Android 실기기에 직접 설치해 주소창 없이 `/app`을 연다.
12. APK에서 카카오 로그인 복귀, `/s/<코드>` 딥 링크, Android 뒤로가기, 백그라운드·종료·실행 중 알림과 클릭 이동이 동작한다. Android 13 이상에서 웹 권한만 허용되고 앱 알림은 차단된 불일치 상태도 탐지해 설정 안내를 보여 준다.
13. 1단계는 신규 유료 계정·도메인·상시 머신을 만들지 않고 완료한다.

### 2단계 — 유료 운영·Google Play 출시(후속 승인 후)

1. 소유 주체·운영 origin·Play 계정 유형·상시 작업자 예산을 사용자가 승인한다.
2. 프로덕션 패키지와 서명, 운영 origin, 개인정보 처리방침을 확정하고 Android App Bundle(AAB)을 만든다.
3. `assetlinks.json`을 Play App Signing 인증서로 검증하며 실패 시 Custom Tab이 되는 회귀 테스트가 있다.
4. Fly 운영 환경에서 HTTP 앱과 별개로 작업자가 상시 실행되며 머신 유휴 정지 중에도 예약 시각 허용 오차 2분 안에 발송된다.
5. 일정 수정·삭제, 중복 작업자 실행, 서버 재시작에도 중복·취소 누락이 없고 404/410 구독 정리와 최대 3회 재시도가 동작한다.
6. Play의 필수 앱 콘텐츠, 개인정보 처리방침, Data safety, 심사 접근 방법과 스토어 자산을 제출한다.
7. 내부·비공개 테스트에서 중대 결함이 없고 계정에 적용되는 테스트 요건을 충족한 뒤 프로덕션 배포한다.

### 3단계 — iOS 후속

1. iOS 16.4 이상 Safari에서 홈 화면에 추가한 웹 앱으로 알림 동의를 받고 동일한 표준 Web Push가 동작한다.
2. 사용자 클릭 안에서만 권한을 요청하고 앱 종료·실행 중 수신 및 알림 클릭 이동을 확인한다.
3. iOS 홈 화면 앱의 별도 저장소 때문에 기존 Safari 로그인·직원 링크가 자동 공유되지 않음을 안내하고 `/app`에서 다시 선택하게 한다.
4. 이번 후속은 홈 화면 PWA까지다. iOS App Store 포장은 별도 사용자 결정과 기획을 거친다.

## 12. 구현 영향 범위

- 프런트: 앱 시작 화면, 공통 manifest·아이콘, 서비스 워커, 알림 카드·설정, 딥 링크 처리.
- 서버: 구독·시험 발송 API, 근무표 게시 outbox, 관리자 리마인더 작업자, 정리 작업.
- DB: `push_subscriptions`, `push_topics`, `notification_outbox` 마이그레이션과 삭제 연계.
- 배포: 1단계 VAPID secret·개발용 `assetlinks.json`; 2단계 Fly 상시 작업자·안정된 운영 origin.
- Android: 1단계 Bubblewrap 프로젝트·디버그 APK; 2단계 AAB 서명·버전·Play Console 항목과 테스트 트랙.
- QA: 웹·TWA·실기기·권한 상태·앱 생명주기·기존 `/s/` PWA 전환 통합 확인 1회.

## 13. 확정 사항과 후속 사용자 결정

### 13.1 지금 적용하는 확정·안전 기본값

| 항목 | 적용안 | 근거·영향 |
|---|---|---|
| 비용 시점 | **1단계에는 새 비용을 만들지 않고, Play 계정·유료 서비스는 2단계로 보류** | 2026-10-20 사용자 결정. 현재 Fly 개발 주소, 표준 Web Push, 직접 설치 APK로 검증 |
| 앱 수 | **관리자·직원 단일 앱** | 역할별 두 앱은 패키지·서명·업데이트·QA를 이중화하고 같은 기기의 중복 설치를 유발 |
| 잠금 화면 정보 | **일반 문구만 표시** | 개인정보 보호 기본값. 상세 제목·근무 시각을 표시하려면 별도 사용자 동의와 정책 변경 필요 |
| 직원 구독 연결 | **공유 링크 단위, 직원 이름 저장 안 함** | 익명 화면의 이름 선택은 본인 인증이 아니므로 개인별 연결을 금지하는 안전 기본값 |
| Android/iOS 순서 | **Android 개발 APK → Android Play → iOS 홈 화면 PWA** | 2026-10-20 사용자 결정. iOS App Store는 포함하지 않음 |

### 13.2 2단계 착수 전에 `dev-lead`가 다시 받아야 하는 결정

| 결정 항목 | 추천안 | 다른 선택과 영향 |
|---|---|---|
| 운영 origin | **소유한 커스텀 도메인을 TWA·Web Push 운영 주소로 고정** | 현재 `*.fly.dev`를 그대로 출시할 수도 있으나 앱 이름 변경·호스트 이전 때 설치 앱, DAL, 카카오 설정과 링크를 함께 바꿔야 함 |
| Play 개발자 계정 | **서비스 소유 주체의 조직 계정** | 개인 계정은 개인 정보가 표시·검증되고 신규 계정의 12명/14일 테스트 요건이 적용될 수 있음. 조직 계정은 D-U-N-S 등 조직 검증 필요. 등록비 발생 |
| 리마인더 운영비 | **Fly 상시 `push-worker`를 두고 2분 내 발송** | 예약 실행 간격을 늘리면 지연이 커지고, 현재 유휴 정지 HTTP 머신만 쓰면 정시 발송을 보장할 수 없음 |
| iOS의 최종 배포 형태 | **홈 화면 PWA + Web Push까지만** | App Store 등록까지 원하면 Apple 계정·심사·포장 방식·비용을 별도 결정해야 함 |
