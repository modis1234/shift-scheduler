# 메인 기능 탭 구분 기획서

상태: v0.4 개인정보 저장 결정 확정·구현 중, 자연어 패턴 자동 등록 기획 추가(2026-10-19). 대상 브랜치 `feature/calendar-share`.

## 1. 목적과 사용자

- **목적**: 한 화면에 이어진 “저장된 근무표 관리”와 “새 근무표 만들기”를 분리하고 관리자 개인 캘린더를 추가해, IT에 익숙하지 않은 매장 관리자가 지금 할 일을 바로 고르게 한다.
- **사용자**: 로그인한 매장 관리자. 현재 계정·권한 모델(계정 1개 = 매장 1곳 = 관리자 1명)은 바꾸지 않는다.
- **핵심 과업**
  1. 근무 조건을 입력하고 근무표를 만든다.
  2. 저장한 근무표를 다시 열고 게시·게시 취소·삭제한다.
  3. 직원 공유 링크를 만들거나 새로 만든다(베타가 켜진 경우).
  4. 관리자 본인의 일정을 달력에서 추가·수정·삭제하고 다른 기기에서도 다시 본다.
- 범위 밖: 직원 화면(`/s/<공유 코드>`)의 내비게이션, URL별 별도 페이지, 새 권한, 반복 일정, 알림, 외부 캘린더 연동, 관리자 개인 일정과 생성 근무표의 자동 연결.

## 2. 현재 화면 분석

현재 `/`의 `ScheduleRunner`는 아래 순서로 모든 기능을 한 번에 보여 준다.

```
헤더
└ 저장된 근무표 + 직원 공유 링크
└ ① 근무 조건 입력
└ ② 근무표 만들기
└ ③ 결과(직원별 표/달력, 저장·게시·삭제)
```

- 관리자가 매달 가장 먼저 하는 “근무표 만들기”보다 저장 목록이 먼저 보여 과업 순서와 UI 가이드의 `① → ② → ③` 원칙이 어긋난다.
- 입력 폼과 결과가 길어 저장 목록으로 돌아가려면 긴 세로 이동이 필요하다. 모바일에서 더 두드러진다.
- 반대로 저장 목록을 별도 URL로 옮기면 현재 `ScheduleRunner`가 가진 입력 문자열, 생성 결과, 보기 방식, 저장 상태가 컴포넌트 해제와 함께 사라질 수 있다.
- “직원별 표/달력”은 한 결과를 보는 방식이고, “입력 폼/JSON”은 한 입력을 편집하는 방식이다. 둘은 상위 기능 구분이 아니므로 기존 세그먼트·보조 버튼을 유지한다.

## 3. 결정: 페이지형 내비게이션 대신 상위 탭

상위 탭 `[근무표 만들기] [근무표 관리] [내 일정]`을 쓴다. “저장된 근무표”는 게시·삭제·직원 공유까지 포함하므로 탭 이름만 `근무표 관리`로 넓히고, 카드 제목은 기존 `저장된 근무표`를 유지한다.

| 비교 | 상위 탭(선택) | 페이지형 내비게이션 |
|---|---|---|
| 사용자 이해 | 반복하는 세 과업이 한 자리에서 보임 | 별도 페이지로 이동한다는 이해가 필요함 |
| 입력·결과 보존 | 같은 `ScheduleRunner` 안에서 패널만 전환해 그대로 유지 | 라우트 전환 전 별도 저장·복원 장치가 필요함 |
| 모바일 | 세 항목을 3열·두 줄 라벨로 항상 노출 | 햄버거 메뉴나 별도 헤더가 과함 |
| 확장성 | 현재 상위 기능 3개에 적합 | 상위 기능이 4개 이상으로 늘 때 유리 |
| 구현 영향 | 프런트 상태·배치 변경 | 라우트·공유 상태 설계까지 필요 |

탭은 화면의 일부 표현 방식이 아니라 **메인 과업 사이를 전환하는 1단계 내비게이션**이다. 상위 기능이 4개 이상이 되거나 URL 공유 요구가 생기면 페이지형 내비게이션으로 다시 검토한다.

## 4. 사용자 흐름

### 4.1 새 근무표 만들기

1. 로그인 후 기본으로 `[근무표 만들기]` 탭이 열린다.
2. `① 근무 조건 입력 → ② 근무표 만들기 → ③ 결과`를 현재와 같은 순서로 수행한다.
3. `[저장]`하면 결과는 화면에 남고 저장 상태가 `작성 중`으로 바뀐다.
4. `[근무표 관리]`나 `[내 일정]` 탭으로 갔다가 돌아와도 입력, 결과, 직원별 표/달력 선택, 저장 상태와 안내·오류가 그대로다.

### 4.2 저장된 근무표 열기

1. `[근무표 관리]` 탭에서 기간과 상태를 보고 한 행을 누른다.
2. 현재 작업에 저장하지 않은 변경이 없으면 바로 `[근무표 만들기]` 탭으로 이동해 해당 입력과 결과를 연다.
3. 저장하지 않은 결과 또는 입력 변경이 있으면 먼저 확인한다.
   - 제목: `저장된 근무표 열기`
   - 본문: `현재 입력과 저장하지 않은 결과가 바뀝니다. 저장된 근무표를 열까요?`
   - 버튼: `[취소] [열기]`
4. 열기가 끝나면 `③ 결과` 제목으로 포커스를 옮긴다. 실패하면 저장 목록 탭에 남아 오류를 보여 준다.

### 4.3 직원 공유 링크 관리

- `STAFF_SHARE_BETA=1`일 때만 `[근무표 관리]` 탭의 목록 아래에 둔다.
- 공유 링크는 특정 작성 화면이 아니라 게시된 근무표 전체를 직원에게 보여 주는 매장 단위 기능이므로 만들기 탭에 두지 않는다.
- 링크 복사·새로 만들기 정책과 문구는 `docs/planning/calendar.md` 7-3절을 유지한다.

### 4.4 내 일정 관리

1. `[내 일정]` 탭을 열면 이번 달 달력과 오늘이 선택된 일별 목록이 보인다.
2. 날짜를 고르고 `[일정 추가]`를 누르면 제목, 하루 종일 여부, 시간, 메모를 입력하는 대화상자가 열린다.
3. `[저장]`하면 서버에 저장되고 선택한 날짜의 달력 칸과 일별 목록에 즉시 나타난다.
4. 기존 일정을 누르면 같은 대화상자에서 수정하거나 `[삭제]`할 수 있다. 삭제 전에는 `이 일정을 삭제할까요? 삭제하면 되돌릴 수 없습니다.`를 확인한다.
5. 이 일정은 로그인한 매장 관리자에게만 보이며, 생성 근무표·직원 공유 화면·근무표 만들기 계산에는 포함되지 않는다.

## 5. 화면과 문구

### 5.1 공통 헤더와 상위 탭

```
┌ 교대근무 스케줄러 · 설명             근무 기간 …  매장명 [로그아웃] ┐
├──────────────────────────────────────────────────────────┤
│ [ 근무표 만들기 ] [ 근무표 관리 ] [ 내 일정 ]                 │
└──────────────────────────────────────────────────────────┘
```

- 탭은 헤더 바로 아래, 본문 최대 폭과 같은 정렬선에 둔다.
- 선택 탭: accent 글자 + 아래 2px 선 + 글자 600. 비선택 탭: muted 글자. 그라데이션·큰 그림자는 쓰지 않는다.
- 데스크톱에서는 헤더와 함께 화면 위에 유지한다. 모바일(≤640px)은 기존 헤더와 같이 sticky를 끈다.
- `[근무표 만들기]` 탭에서만 헤더의 `근무 기간` 칩을 보인다. 근무표 관리나 개인 일정을 보는 동안 작업 중 기간으로 오해되지 않게 숨긴다.
- 매장 이름과 `[로그아웃]`은 세 탭 모두 보인다.

### 5.2 근무표 만들기 탭

기존 `① 근무 조건 입력`, `② 근무표 만들기`, `③ 결과`를 내용·순서·문구 변경 없이 옮긴다.

| 상태 | 화면 |
|---|---|
| 정상 | 입력 카드 → 만들기 바 → 결과 카드 |
| 아직 만들지 않음 | `아직 만든 근무표가 없습니다. 근무 조건을 확인한 뒤 [근무표 만들기]를 누르세요.` |
| 만드는 중 | 버튼 `근무표 만드는 중…`, 결과 영역에 예상 시간 |
| 입력 오류 | 기존 `확인이 필요한 항목 N건`과 입력 이동 동작 유지 |
| 요청 오류 | 기존 상황별 오류 문구 유지. 탭을 바꿔도 사라지지 않음 |
| 저장 성공·실패 | 기존 안내 문구와 화면의 결과 유지 |

### 5.3 근무표 관리 탭

```
┌ 저장된 근무표 ─────────────────────────────────────┐
│ 11월 1일 ~ 11월 30일  ● 게시됨            만든 날 10월 19일 │
│ 12월 1일 ~ 12월 31일  ● 작성 중            만든 날 10월 19일 │
└──────────────────────────────────────────────────┘
┌ 직원 공유 링크 (베타가 켜졌을 때만) ─────────────────────┐
│ https://…                                  [복사] [새로 만들기] │
│ 게시된 근무표만 직원에게 보입니다.                         │
└──────────────────────────────────────────────────┘
```

| 상태 | 화면 |
|---|---|
| 정상 | 기간, 상태 배지, 만든 날을 가진 카드형 행 목록 |
| 현재 열어 둔 항목 | accent 테두리와 배경, `aria-current="true"` |
| 로딩 | 스켈레톤 3줄, 컨테이너 `aria-busy="true"` |
| 빈 목록 | `저장된 근무표가 없습니다. [근무표 만들기] 탭에서 근무표를 만든 뒤 저장해 주세요.` + 보조 버튼 `[근무표 만들기]` |
| 목록 오류 | `저장된 근무표를 불러오지 못했습니다. 잠시 뒤 다시 시도해 주세요.` + `[다시 시도]` |
| 열기 중 | 누른 행을 비활성화하고 행 안에 `근무표 여는 중…` |
| 열기 실패 | 목록 탭 유지. `근무표를 불러오지 못했습니다. 목록을 새로 고친 뒤 다시 시도해 주세요.` |
| 공유 링크 로딩·없음·오류 | 기존 `SavedSchedules.ShareLink` 상태와 문구 유지 |

### 5.4 내 일정 탭

화면 제목은 `내 일정`, 설명은 `매장 관리자 본인의 일정입니다. 직원 근무표에는 반영되지 않습니다.`로 고정한다. 메뉴·화면 어디에서도 `내 스케줄`이나 `근무표`라고 부르지 않아 생성 결과 달력과 구분한다.

```
┌ 내 일정 ────────────────────────────────────────────────┐
│ 매장 관리자 본인의 일정입니다. 직원 근무표에는 반영되지 않습니다. │
│ [‹ 이전 달]      [오늘]      2026년 11월      [다음 달 ›] │
│ 일   월   화   수   목   금   토                              │
│ 1    2    3    4    5    6    7                              │
│      발주  교육                                             │
│ …                                                           │
└──────────────────────────────────────────────────────────┘
┌ 11월 3일 (화) ─────────────────────────── [일정 추가] ┐
│ 10:00 직원 교육                                              │
│ 하루 종일 소방 점검                                           │
└──────────────────────────────────────────────────────────┘
```

- 기본은 월 달력이다. `[‹ 이전 달] [오늘] [다음 달 ›]`로 이동한다.
- 데스크톱 달력 칸에는 시간과 제목을 최대 2개까지 보이고 나머지는 `외 N개`로 표시한다.
- 모바일 달력 칸에는 제목 대신 일정이 있음을 나타내는 점과 `N개`만 보인다. 선택 날짜의 전체 일정은 달력 아래 일별 목록에서 본다.
- 오늘은 accent 2px 테두리 + `오늘`, 선택 날짜는 accent-soft 배경으로 구분한다. 둘이 같으면 두 표시를 모두 유지한다.
- 개인 일정에는 근무조 색을 쓰지 않는다. 중립 표면 + accent 점을 써 생성 근무표의 오픈·미들·마감 색과 혼동하지 않게 한다.

| 상태 | 화면 |
|---|---|
| 정상 | 월 달력 + 선택 날짜의 시간순 일정 + `[일정 추가]` |
| 일정 없음 | 일별 목록에 `이 날짜에 등록한 일정이 없습니다.` + `[일정 추가]` |
| 월 전체 비어 있음 | 달력은 그대로 보이고 설명 아래 `등록한 일정이 없습니다. 날짜를 선택해 일정을 추가해 보세요.` |
| 불러오는 중 | 달력 높이를 유지한 스켈레톤, `aria-busy="true"` |
| 불러오기 실패 | `일정을 불러오지 못했습니다. 잠시 뒤 다시 시도해 주세요.` + `[다시 시도]` |
| 저장 중 | 대화상자 `[저장하는 중…]`, 닫기·중복 제출 방지 |
| 저장 실패 | 대화상자를 유지하고 `일정을 저장하지 못했습니다. 입력한 내용은 그대로 두었습니다. 잠시 뒤 다시 시도해 주세요.` |
| 삭제 중·실패 | `[삭제하는 중…]`; 실패 시 일정과 대화상자를 유지하고 오류 표시 |

**일정 추가·수정 대화상자**

| 필드 | 규칙 |
|---|---|
| 일정 제목 | 필수, 앞뒤 공백 제거, 1~50자. 예: `직원 교육` |
| 날짜 | 필수, 선택한 날짜로 미리 채움. `YYYY-MM-DD` 전송 |
| 하루 종일 | 기본 선택. 선택하면 시작·종료 시각을 숨기고 저장값은 `null` |
| 시작/종료 시각 | 하루 종일이 아닐 때 둘 다 필수, `HH:MM`, 같은 날짜에서 종료 > 시작 |
| 메모 | 선택, 앞뒤 공백 제거, 최대 200자 |

- 추가 제목 `일정 추가`, 수정 제목 `일정 수정`.
- 버튼은 추가 `[취소] [저장]`, 수정 `[삭제] [취소] [저장]`.
- 제목 오류 `일정 제목을 입력해 주세요.`, 시간 오류 `종료 시각은 시작 시각보다 늦어야 합니다.`, 길이 오류는 `일정 제목은 50자까지 입력할 수 있습니다.` / `메모는 200자까지 입력할 수 있습니다.`

## 6. 상태 보존·예외 정책

1. 활성 탭은 `ScheduleRunner`의 클라이언트 상태로 둔다. 기본값은 `근무표 만들기`다.
2. 탭 전환은 입력·결과 패널을 **언마운트하거나 초기화하지 않는다**. `text`, `mode`, `run`, `resultView`, `saved`, 안내·오류 상태를 모두 유지한다.
3. 저장 목록도 탭 전환만으로 다시 요청하지 않는다. 최초 진입과 저장·게시·게시 취소·삭제 후에만 기존 `refreshKey` 규칙으로 갱신한다.
4. 탭 전환 자체에는 확인창을 띄우지 않는다. 데이터를 바꾸지 않기 때문이다.
5. 저장된 근무표를 여는 행동만 현재 작업을 바꾼다. 보호 대상은 아래 중 하나다.
   - 생성했지만 아직 저장하지 않은 결과가 있음
   - 마지막으로 열거나 생성·저장한 입력 이후 입력값이 바뀜
6. 보호 대상이 없으면 확인 없이 연다. 확인의 기본 포커스는 `[취소]`다.
7. 탭 전환 후 새로고침까지 작업 결과를 보존하는 기능은 이번 범위가 아니다. 로그인 만료 시 입력 보존은 기존 `sessionStorage` 정책을 유지한다.
8. 목록을 열어 입력과 결과를 교체한 뒤에도 저장·게시·삭제 API와 정책은 바꾸지 않는다.
9. 내 일정은 저장 성공 응답을 받은 뒤에만 달력에 확정 반영한다. 실패하면 입력 대화상자를 닫거나 기존 일정을 지우지 않는다.
10. 내 일정에서 다른 탭으로 이동해도 보고 있던 달과 선택 날짜를 유지한다. 작성 중이지만 저장하지 않은 대화상자가 있으면 `작성 중인 일정이 있습니다. 닫고 이동할까요?`를 확인한다.

## 7. 모바일·키보드 접근성

- 모바일에서 세 탭을 같은 폭 3열로 배치한다. `근무표 만들기`와 `근무표 관리`는 두 줄로 줄바꿈하고 `내 일정`은 한 줄로 가운데 정렬한다. 각 터치 영역 높이는 최소 52px이며 페이지 전체 가로 스크롤이 생기지 않는다.
- 마크업은 `role="tablist"`(이름: `메인 기능`), `role="tab"`, `aria-selected`, `aria-controls`, `role="tabpanel"`, `aria-labelledby`를 연결한다.
- `Tab`은 선택된 탭 하나에만 들어간다. `←/→`로 탭을 이동·선택하고, `Home/End`로 처음·마지막 탭을 선택한다. 세 패널 모두 선택 즉시 표시한다.
- 비선택 탭은 `tabIndex=-1`. 숨긴 패널의 입력·버튼은 키보드와 스크린리더 탐색에서 제외한다(`hidden`). React 컴포넌트 상태는 유지한다.
- 마우스·터치로 탭을 바꾸면 포커스는 누른 탭에 남는다. 빈 상태의 `[근무표 만들기]` 버튼은 탭을 바꾼 뒤 `① 근무 조건 입력` 제목으로 포커스를 옮긴다.
- 저장 행을 열었을 때는 네트워크 응답 뒤 `③ 결과` 제목으로 포커스를 옮긴다. 열기 실패 시 오류 상자로 포커스를 옮긴다.
- 선택 여부를 색만으로 전달하지 않고 `aria-selected`와 아래 선을 함께 쓴다. UI 가이드의 대비, 포커스 링, reduced motion, 다크 모드를 그대로 적용한다.
- 내 일정의 월 달력은 `role="grid"`, 요일은 열 머리글, 날짜는 버튼으로 구현한다. 선택 날짜 버튼에 `aria-selected="true"`, 오늘에 `aria-current="date"`를 쓴다.
- 달력 날짜는 `←/→` 하루, `↑/↓` 7일, `PageUp/PageDown` 이전·다음 달, `Home/End` 주의 처음·마지막 날로 이동한다. 월을 넘으면 필요한 월 데이터를 불러오고 포커스를 같은 날짜에 유지한다.
- 날짜 버튼의 접근 가능한 이름은 `11월 3일 화요일, 일정 2개` 형식이다. `Enter`는 날짜를 선택해 아래 일별 목록 제목으로 포커스를 옮긴다. 일정 행의 `[수정]`은 숨기지 않고 키보드로 접근 가능하게 한다.

## 9. 내 일정 데이터 영속화와 최소 계약

브라우저 상태만 쓰면 새로고침·로그아웃·다른 기기에서 일정이 사라져 “저장”이라는 사용자 기대를 충족하지 못한다. 기존에 선택한 Supabase Postgres(`DATABASE_URL`)에 영속화한다. 새 외부 서비스나 의존성은 추가하지 않는다.

### 9.1 저장 범위와 개인정보

- 일정은 현재 계정 모델에 맞춰 `store_id`에 속한다. 로그인한 관리자는 자기 매장 일정만 조회·변경할 수 있다. `store_id`는 요청 본문을 믿지 않고 세션에서 정한다.
- 저장 항목은 제목, 날짜, 하루 종일 여부, 시작·종료 시각, 메모, 생성·수정 시각이다.
- 직원 공유 API와 `/s/<공유 코드>`에는 절대 포함하지 않는다. 근무표 생성 API에도 보내지 않는다.
- 제목·메모에는 개인 정보가 들어갈 수 있으므로 개인정보 처리방침의 저장 항목과 삭제 방법에 “관리자 개인 일정(제목·메모·일시)”을 추가한다.
- 보관 기간은 관리자가 삭제하거나 매장 계정을 삭제할 때까지다. 매장 삭제 시 함께 삭제한다. 이번 범위에 자동 만료는 넣지 않는다.
- 반복 일정, 참석자, 첨부, 알림, 색, 여러 날에 걸친 일정, 외부 캘린더 연동은 최소 구현에서 제외한다.

### 9.2 DB

기존 migration 다음 번호에 추가한다. `stores.id`의 실제 타입은 기존 스키마와 같게 쓴다.

```sql
CREATE TABLE IF NOT EXISTS manager_events (
  id text PRIMARY KEY,
  store_id text NOT NULL REFERENCES stores(id) ON DELETE CASCADE,
  event_date date NOT NULL,
  title varchar(50) NOT NULL,
  all_day boolean NOT NULL DEFAULT true,
  start_time time NULL,
  end_time time NULL,
  note varchar(200) NOT NULL DEFAULT '',
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  CHECK ((all_day AND start_time IS NULL AND end_time IS NULL)
      OR (NOT all_day AND start_time IS NOT NULL AND end_time IS NOT NULL AND end_time > start_time))
);

CREATE INDEX IF NOT EXISTS manager_events_store_date_idx
  ON manager_events(store_id, event_date, start_time);

ALTER TABLE manager_events ENABLE ROW LEVEL SECURITY;
```

- `id`는 서버에서 `randomUUID()`로 만들고 기존 id 규칙처럼 text로 저장한다. RLS 정책은 만들지 않아 Supabase Data API에서는 읽을 수 없고 서버의 DB 연결만 사용한다.
- 날짜와 시각은 매장 현지의 벽시계 값이다. v0.1은 하루 안에서 끝나는 일정만 지원해 시간대 변환을 하지 않는다.
- 같은 제목·시간의 중복 일정도 허용한다. 사용자가 각각 수정·삭제할 수 있다.

### 9.3 API

모든 응답은 로그인 필요, 기존 세션 사용, `Cache-Control: no-store`다. 다른 매장의 id는 존재 여부를 드러내지 않고 404로 답한다.

| 요청 | 계약 |
|---|---|
| `GET /api/manager-events?from=YYYY-MM-DD&to=YYYY-MM-DD` | 양 끝 포함, 최대 42일. `event_date`, 하루 종일 우선, `start_time`, `created_at` 순으로 정렬한 배열 |
| `POST /api/manager-events` | 아래 입력 검증 후 201로 생성 객체 반환 |
| `PATCH /api/manager-events/<id>` | 전체 편집 가능 필드를 받아 검증 후 200으로 수정 객체 반환 |
| `DELETE /api/manager-events/<id>` | 확인은 화면에서 하고 서버 삭제 후 204 |

요청·응답 객체:

```ts
type ManagerEvent = {
  id: string;
  date: string;             // YYYY-MM-DD
  title: string;            // 1~50자
  allDay: boolean;
  startTime: string | null; // HH:MM, allDay이면 null
  endTime: string | null;   // HH:MM, allDay이면 null
  note: string;             // 0~200자
  createdAt: string;
  updatedAt: string;
};

type ManagerEventWrite = Omit<ManagerEvent, "id" | "createdAt" | "updatedAt">;
```

- `from`, `to`가 없거나 형식이 틀리거나 42일을 넘으면 400 `조회할 날짜 범위를 확인해 주세요.`
- 본문 검증 실패는 400과 필드별 오류를 반환한다. 화면에는 5.4절의 관리자 언어 문구를 쓴다.
- 인증 없음은 기존 규칙대로 401. DB 오류는 원문을 노출하지 않고 500 `일정을 처리하지 못했습니다.`
- 동시에 수정되면 마지막 저장이 우선한다. 현재 계정 1개 = 관리자 1명 범위에서는 충돌 UI를 추가하지 않는다.

## 11. 완료 기준

1. 로그인 후 `/`에서 상위 탭 `[근무표 만들기] [근무표 관리] [내 일정]`이 보이고 기본 선택은 `[근무표 만들기]`다.
2. 만들기 탭에는 기존 `① 입력 → ② 만들기 → ③ 결과`만, 관리 탭에는 저장 목록과 베타 공유 링크만, 내 일정 탭에는 개인 월 달력만 보인다.
3. 입력을 수정하거나 결과를 만든 뒤 탭을 왕복해도 입력, 결과, 직원별 표/달력 선택, 저장 상태, 안내·오류가 그대로다.
4. 탭 왕복만으로 저장 목록 API를 반복 호출하지 않는다.
5. 저장 목록의 행을 열면 만들기 탭으로 이동하고 해당 입력·결과가 보이며 `③ 결과` 제목에 포커스가 간다.
6. 저장하지 않은 입력 변경 또는 결과가 있을 때 저장 항목을 열면 확인창이 나오고, `[취소]`하면 현재 작업과 활성 탭이 그대로다.
7. 빈 저장 목록에는 새 문구와 `[근무표 만들기]` 버튼이 보이고, 버튼을 누르면 만들기 탭의 `① 근무 조건 입력`으로 이동한다.
8. 목록 로딩·오류·열기 중·열기 실패 상태가 5.3절 문구와 동작을 따른다.
9. 모바일 320px 폭에서 탭 세 개가 3열로 보이고 페이지 전체 가로 스크롤이 없으며, 터치 영역이 52px 이상이다.
10. 키보드 `Tab`, `←/→`, `Home/End`로 탭을 선택할 수 있고 ARIA 연결이 유효하다. 숨긴 패널의 컨트롤은 탐색되지 않는다.
11. 라이트·다크 모드, 포커스 표시, reduced motion, 인쇄에서 기존 UI 가이드 기준을 지킨다. 인쇄 시 상위 탭과 저장 목록은 보이지 않고 기존 근무표 인쇄 결과는 바뀌지 않는다.
12. 기존 근무표 만들기·저장·게시·게시 취소·삭제·직원 공유 링크 동작과 API 계약에 회귀가 없다.
13. 내 일정의 이전 달·오늘·다음 달 이동, 날짜 선택, 정상·빈·로딩·오류 상태가 5.4절대로 보인다.
14. 하루 종일 일정과 시간 일정의 추가·수정·삭제가 동작하고, 새로고침·로그아웃 후 재로그인·다른 기기에서도 저장된 일정이 보인다.
15. 제목·날짜·시간·메모 검증이 화면과 서버 양쪽에서 적용되고 저장 실패 시 입력, 삭제 실패 시 기존 일정이 유지된다.
16. 다른 매장 세션으로 일정 id를 조회·수정·삭제할 수 없고, 직원 공유 API와 생성 근무표 입력·결과에 관리자 개인 일정이 포함되지 않는다.
17. 내 일정 달력을 키보드 방향키·PageUp/PageDown·Home/End·Enter로 조작할 수 있고 날짜·일정 수가 스크린리더 이름에 포함된다.
18. DB migration을 새 DB에 적용한 뒤 CRUD API 실제 호출이 성공하며, 매장 삭제 시 관련 일정도 삭제된다.

## 13. 자연어 패턴 일정 자동 등록

### 13.1 목적과 기술 결정

사용자가 시작일·종료일과 짧은 한국어 패턴을 입력하면, 해당 범위에 반복되는 개인 일정을 계산해 미리 보여 주고 확인 후 한 번에 저장한다.

**v0.1 추천안은 외부 LLM이 아닌 결정적 한국어 패턴 파서다.** `2일 근무하고 1일 쉬기`처럼 범위가 분명한 반복 규칙은 생성형 AI보다 규칙 파서가 정확하고 설명 가능하며, 같은 입력이 항상 같은 결과를 만든다. 화면 명칭도 실제 구현을 정직하게 나타내는 `문장으로 여러 일정 만들기`로 한다. `AI가 만들기`라고 표기하지 않는다.

| 항목 | 결정적 한국어 패턴 파서(추천) | 외부 LLM 호출 |
|---|---|---|
| 이해 범위 | 지원 문법 안에서만 동작, 모호하면 명시적 오류 | 다양한 표현을 이해할 가능성이 높음 |
| 결과 안정성 | 같은 입력 = 같은 결과, 날짜 계산 테스트 가능 | 모델·버전에 따라 결과가 달라질 수 있음 |
| 비용·속도 | 호출비·API 키 없음, 즉시 계산 | 호출당 비용·지연·요청 제한이 있음 |
| 실패 | 미지원 문법을 바로 안내 | 모델 장애·시간 초과·잘못된 구조화 응답이 추가됨 |
| 개인정보 | 문장을 외부 업체로 보내지 않음 | 일정 문장에 포함된 이름·업무가 외부 처리자에게 전달될 수 있음 |
| 운영 | 일반 코드 배포만 필요 | 서버 전용 API 키, 비용 한도, 공급자 장애 대응, 개인정보 처리 고지가 필요 |

- 실제 외부 LLM은 v0.1에 도입하지 않으므로 새 외부 서비스·API 키·비용이 없다.
- 사용자가 생성형 AI의 자유로운 문장 이해를 꼭 원하면 구현 전에 공급자·모델, 월 비용 상한, 데이터 처리 지역·보관/학습 제외 조건을 선택받는다. 키는 서버 환경변수에만 두고, 구조화 출력도 아래 결정적 검증기를 반드시 통과시켜야 한다.
- 외부 LLM 실패 시 임의 결과를 저장하거나 규칙 파서 결과인 척하지 않는다. `문장을 해석하지 못했습니다. 지원 예시대로 다시 입력해 주세요.`로 끝낸다.

### 13.2 사용자 흐름과 화면

`내 일정`의 `[일정 추가]` 옆에 `[여러 일정 만들기]` 보조 버튼을 둔다.

1. `[여러 일정 만들기]`를 누르면 입력 대화상자가 열린다.
2. 시작일, 종료일, 한 줄 패턴 문장(최대 100자)을 입력하고 `[일정 미리보기]`를 누른다.
3. 서버가 문장을 결정적으로 해석하고 기존 일정과 비교한 미리보기를 반환한다. 이 단계에서는 DB를 바꾸지 않는다.
4. 사용자는 요약과 날짜별 결과, 겹치는 날짜, 건너뛸 중복을 확인한다.
5. `[N개 일정 등록]`을 누르면 서버가 같은 입력을 다시 계산해 하나의 트랜잭션으로 저장한다.
6. 성공하면 대화상자를 닫고 달력을 새로 고친 뒤 `N개 일정을 등록했습니다. 중복 M개는 건너뛰었습니다.`를 `role="status"`로 알린다.

```
┌ 문장으로 여러 일정 만들기 ────────────────────────────────┐
│ 시작일 [2026-11-01]   종료일 [2026-11-30]                   │
│ 패턴 문장                                                    │
│ [ 오늘 날짜부터 2일은 근무하고 하루는 쉬는 패턴으로 일정을 등록해줘 ] │
│ 지원 예시: “2일 근무하고 1일 쉬기”                           │
│                                         [취소] [일정 미리보기] │
└──────────────────────────────────────────────────────────┘

┌ 미리보기: 11월 1일~30일 ─────────────────────────────────┐
│ 2일 근무 + 1일 쉬는 날을 반복합니다.                         │
│ 새 일정 28개 · 중복으로 건너뜀 2개 · 기존 일정 있는 날 3일    │
│ 11월 1일  근무        새 일정                                 │
│ 11월 2일  근무        기존 일정 있음                          │
│ 11월 3일  쉬는 날     중복 — 등록하지 않음                    │
│ …                                                             │
│                             [입력 수정] [28개 일정 등록]        │
└──────────────────────────────────────────────────────────┘
```

| 상태 | 화면·문구 |
|---|---|
| 초기 | 시작일과 `referenceDate`는 브라우저 현지 오늘, 종료일은 비어 있음. 패턴 예시 표시 |
| 해석 중 | 버튼 `미리보는 중…`, 입력 비활성, `aria-busy="true"` |
| 미지원 문법 | `문장을 해석하지 못했습니다. “2일 근무하고 1일 쉬기”처럼 입력해 주세요.` |
| 오늘 불일치 | `문장의 “오늘 날짜부터”와 시작일이 다릅니다. 시작일을 오늘로 바꾸거나 문장에서 해당 표현을 빼 주세요.` |
| 날짜 오류 | `종료일은 시작일과 같거나 뒤여야 합니다.` |
| 기간 초과 | `한 번에 만들 수 있는 기간은 최대 90일입니다.` |
| 미리보기 정상 | 정규화한 규칙, 새 일정·중복·겹침 수, 날짜별 목록 |
| 새 일정 0개 | `등록할 새 일정이 없습니다. 같은 일정이 이미 등록되어 있습니다.` 등록 버튼 숨김 |
| 저장 중 | 버튼 `일정 등록하는 중…`, 닫기·중복 제출 방지 |
| 기존 일정 변경 | `기존 일정이 바뀌었습니다. 새 미리보기를 확인해 주세요.` 후 미리보기 갱신 |
| 저장 실패 | `일정을 등록하지 못했습니다. 새로 등록된 일정은 없습니다. 잠시 뒤 다시 시도해 주세요.` |

미리보기는 12개 행 높이에서 내부 스크롤한다. 90일 전체를 생략하지 않고 확인할 수 있으며, 요약만 보고도 새 일정·중복·겹침 수를 알 수 있다.

### 13.3 지원 문법과 계산 규칙

지원하는 문장 구조는 아래 하나다. 공백·쉼표·마침표 차이와 아래 예시의 표현만 허용한다.

```
[오늘부터|오늘 날짜부터|시작일부터]
<일수>[은|는] <일정 제목> [하고|후]
<일수>[은|는] [쉬기|쉬는 날|쉬는 패턴|휴무] [반복]
[으로 일정을 등록해줘|으로 일정을 등록해 주세요]

<일수> = 1~30의 아라비아 숫자 + "일" 또는 "하루"(1일)
```

지원 예시:

- `2일 근무하고 1일 쉬기` → 제목 `근무`, 2일 등록 + `쉬는 날` 1일
- `오늘부터 2일 근무하고 1일 쉬는 패턴` → 선택한 시작일부터 같은 계산
- `3일 야간 근무 후 2일 휴무 반복` → 제목 `야간 근무`, 3일 등록 + `쉬는 날` 2일
- `오늘 날짜부터 2일은 근무하고 하루는 쉬는 패턴으로 일정을 등록해줘` → **사용자 원문 필수 호환**, 오늘부터 2일 `근무` + 1일 `쉬는 날` 반복

규칙:

1. 시작일·종료일 필드는 필수이고 계산의 날짜 기준이다. 대화상자를 열 때 `referenceDate`와 시작일을 브라우저 현지 오늘로 채운다. 문장에 `오늘부터` 또는 `오늘 날짜부터`가 있으면 `startDate === referenceDate`여야 하며, 다르면 “오늘 불일치” 오류로 거부한다. `시작일부터`는 선택한 시작일을 그대로 쓴다.
2. 일수는 아라비아 숫자 `1일`~`30일`과 `하루`만 지원한다. `하루`는 1일로 정규화한다. 일수 뒤의 조사 `은`·`는`은 선택이며 계산에 영향을 주지 않는다. `이틀`, `사흘`, `격일`, `월수금`, 공휴일 제외, 시각, 여러 패턴 조합은 v0.1에서 지원하지 않는다.
3. 일정 제목은 앞뒤 공백 제거 후 1~30자이며 저장 시 기존 50자 제한을 그대로 통과해야 한다. 휴식일 제목은 UI 가이드 용어인 `쉬는 날`로 고정한다.
4. 생성 일정은 모두 `하루 종일`, 메모 없음이다. 필요한 일정은 등록 후 한 건씩 기존 수정 화면에서 시각·메모를 바꿀 수 있다.
5. 시작일을 주기의 첫 근무일로 본다. 근무 N일 → 쉬는 날 M일을 종료일까지 반복하고, 마지막 주기가 덜 끝나도 종료일에서 자른다.
6. 시작일·종료일 양 끝을 포함해 1~90일만 허용한다. 최대 생성 수는 90개다.
7. `으로 일정을 등록해줘`, `으로 일정을 등록해 주세요`는 선택 종결어로 제거한 뒤 해석한다. 그 밖의 요청형 종결어는 v0.1에서 지원하지 않는다.
8. 입력 문장은 최대 100자다. 지원하지 않는 내용이 섞이면 일부만 추측하지 않고 전체를 오류로 처리한다.

### 13.4 겹침·중복·부분 실패 정책

- **기존 일정이 있는 날짜**: 다른 제목의 일정은 함께 둘 수 있으므로 새 패턴 일정도 등록한다. 미리보기에 `기존 일정 있음`을 표시하며 기존 일정은 수정·삭제하지 않는다.
- **정확한 중복**: 같은 매장·날짜·제목·하루 종일 일정이 이미 있으면 `중복 — 등록하지 않음`으로 표시하고 자동으로 건너뛴다. 시간 일정은 제목이 같아도 정확한 중복으로 보지 않는다.
- **패턴 내부 중복**: 결정적 계산상 발생하지 않아야 하며 발생하면 서버 오류로 보고 저장하지 않는다.
- **동시 변경**: 미리보기 뒤 기존 일정이 바뀌어 결과 요약이 달라지면 409를 반환하고 저장하지 않는다. 사용자는 새 미리보기를 확인해야 한다.
- **부분 실패 없음**: 새 일정 전체를 DB 트랜잭션 하나로 저장한다. 한 건이라도 검증·DB 저장에 실패하면 전부 롤백한다. 중복 건너뛰기는 저장 실패가 아니라 미리보기에서 합의한 정상 결과다.
- 패턴 등록은 기존 일정을 덮어쓰거나 삭제하지 않는다. 등록 후 개별 수정·삭제는 기존 `내 일정` 계약을 따른다.

### 13.5 API 최소 계약

파서와 검증기는 서버 공용 모듈 하나로 두고 미리보기와 저장에서 같은 함수를 사용한다. 원문은 DB나 애플리케이션 로그에 저장하지 않는다.

**미리보기** — `POST /api/manager-events/pattern-preview`

```ts
// request
{ startDate: string; endDate: string; referenceDate: string; patternText: string }

// 200 response
{
  normalized: { workDays: number; restDays: number; workTitle: string };
  summary: { total: number; creatable: number; duplicates: number; datesWithExisting: number };
  events: Array<{
    date: string;
    title: string;
    kind: "work" | "rest";
    status: "new" | "existing-date" | "duplicate";
  }>;
  digest: string;
}
```

**일괄 저장** — `POST /api/manager-events/pattern-batch`

```ts
// request: 미리보기와 같은 원문 + 직전 응답 digest
{ startDate: string; endDate: string; referenceDate: string; patternText: string; expectedDigest: string }

// 201 response
{ created: number; skippedDuplicates: number; events: ManagerEvent[] }
```

- 두 API 모두 로그인 필요, `store_id`는 세션에서 결정, `Cache-Control: no-store`다.
- 서버는 일괄 저장 때 문장을 다시 해석하고 현재 DB와 비교해 digest를 다시 계산한다. digest가 다르면 409이며 저장하지 않는다.
- digest는 정규화한 패턴·기간과 범위 안 기존 일정의 정렬된 비교 서명을 SHA-256으로 계산한다. 인증 수단이 아니라 미리보기 이후 변경 감지용이다.
- 400은 날짜·길이·지원 문법 오류, 401은 로그인 필요, 409는 미리보기 이후 변경, 500은 처리 실패다. 원문·SQL·스택은 응답에 노출하지 않는다.
- 일괄 insert는 트랜잭션으로 실행하고 각 결과는 기존 `manager_events` 구조(`allDay=true`, 시각 `null`, 메모 빈 문자열)를 쓴다. DB migration 변경은 없다.
- 최대 90건 제한은 클라이언트와 서버 양쪽에서 검사한다.

### 13.6 모바일·키보드·접근성

- 모바일에서는 시작일·종료일을 세로로 쌓고 패턴 입력·버튼을 폭 100%로 둔다. 미리보기 행은 `날짜 / 제목 / 상태`가 자연스럽게 줄바꿈되어 페이지 가로 스크롤을 만들지 않는다.
- 입력 대화상자를 열면 제목으로, 검증 오류면 오류 요약으로, 미리보기 성공이면 `미리보기: 시작일~종료일` 제목으로 포커스를 옮긴다.
- 미리보기 목록은 표 또는 목록의 기본 의미 구조를 쓰고, `11월 3일 쉬는 날, 중복으로 등록하지 않음`처럼 상태를 색 없이 읽을 수 있게 한다.
- 중복·기존 일정 있음은 색 + 글자 배지로 표시한다. 요약 변화는 `aria-live="polite"`, 저장 실패는 `role="alert"`다.
- `[N개 일정 등록]`의 N은 실제 새 일정 수와 같아야 한다. 0개면 비활성 대신 버튼을 숨기고 이유 문구를 보여 준다.
- 대화상자 `Esc`와 `[취소]`는 저장 전 언제든 닫을 수 있다. 저장 중에는 닫기를 막아 결과를 알 수 없는 상태를 만들지 않는다.

### 13.8 완료 기준

1. `내 일정`에서 `[여러 일정 만들기]`를 눌러 시작일·종료일·패턴 문장을 입력할 수 있다.
2. `2일 근무하고 1일 쉬기`와 13.3절의 지원 예시가 같은 입력이면 항상 같은 날짜·제목을 만든다.
3. 사용자 원문 `오늘 날짜부터 2일은 근무하고 하루는 쉬는 패턴으로 일정을 등록해줘`가 오늘 시작일에서 2일 `근무` + 1일 `쉬는 날` 반복으로 해석된다.
4. `오늘 날짜부터` 문장의 시작일이 브라우저 현지 오늘과 다르면 구체적인 “오늘 불일치” 오류로 거부된다.
5. `[일정 미리보기]`만으로 DB가 바뀌지 않고, 정규화 규칙·새 일정·중복·기존 일정 있는 날짜 수와 전체 날짜별 결과가 보인다.
6. `[N개 일정 등록]` 후 새 일정만 한 트랜잭션으로 저장되며 달력과 선택 날짜 목록이 갱신된다.
7. 정확한 중복은 미리보기에서 구분되어 건너뛰고, 같은 날짜의 다른 일정은 유지한 채 함께 등록된다.
8. 미리보기 뒤 기존 일정이 바뀌면 409와 새 미리보기 안내가 나오며 어떤 새 일정도 저장되지 않는다.
9. 한 건의 검증·DB 오류를 강제로 만들면 전체 batch가 롤백되어 부분 등록이 없다.
10. 90일을 넘는 범위, 종료일이 앞선 범위, 0·31일 주기, 100자 초과, 미지원 문장은 구체적인 관리자 언어 오류로 거부된다.
11. 자연어 원문이 DB·일반 로그에 남지 않고 외부 서비스로 전송되지 않으며, API 키 환경변수가 새로 필요하지 않다.
12. 모바일 320px에서 입력·미리보기에 페이지 가로 스크롤이 없고, 키보드만으로 입력→미리보기→확인·취소가 가능하며 포커스와 ARIA 상태가 13.6절을 따른다.
13. 기존 단건 일정 CRUD, 월 달력, 근무표 만들기·관리·공유 기능에 회귀가 없다.

### 13.9 외부 LLM 도입 시 사용자 결정 항목

추천안대로 결정적 파서를 구현하면 아래 결정은 필요 없다. 향후 실제 외부 LLM을 도입하려면 구현 전에 dev-lead가 사용자에게 다음을 선택받는다.

| 결정 | 추천 | 영향 |
|---|---|---|
| 공급자·모델 | 국내 처리 지역과 입력 비학습·짧은 보관을 계약으로 보장하는 모델 | 사용 가능 지역·가격·품질·장애 의존성이 달라짐 |
| 비용 상한 | 매장별 월 호출 횟수와 전체 월 예산 설정 | 한도 초과 시 규칙 파서만 제공하거나 기능 중단 필요 |
| 전송 범위 | 이름·메모 없이 패턴 문장과 날짜만 전송 | 자유 문장 품질은 제한될 수 있으나 개인정보 노출 축소 |
| 실패 처리 | 자동 저장 금지, 구조화 응답 검증 후 항상 미리보기 | 한 단계 늘지만 오등록 방지 |

외부 LLM을 선택하면 개인정보 처리방침의 국외 이전·처리 위탁 여부, 공급자 보관·학습 정책, API 키 운영 책임을 별도로 검토한다.

### 13.10 삭제·색 문장 확장 (2026-10-20, 사용자 요청)

외부 LLM 대신(비용 보류) 결정적 파서를 확장했다. 문장에서 아는 표현을 하나씩 떼어 내고 남는 말이 있으면 전체를 거부하는 원칙(13.3 규칙 8)은 그대로다.

- 삭제: `해당일에 일정을 삭제해줘`, `해당 기간에 일정을 삭제하고 …`, `모든 일정을 제거하고 …`, `… 일정 지우고 …`. **삭제 범위는 항상 선택한 시작일~종료일**이며 “모든”도 기간 밖을 지우지 않는다. 종료일을 비우면 시작일 하루다.
- 색: `휴무는 빨간색으로`, `근무는 파란색`(대상별), `빨간색으로`(근무·쉬는 날 모두). 기본은 근무 파랑, 쉬는 날 초록.
- 반복 문법 추가: `2일 근무 하루 휴무`처럼 `하고` 없이, `휴일`·`쉬는`도 휴식어로 허용. `오늘 기준으로`는 `오늘부터`와 같게 처리하고 오늘 불일치 검사를 적용한다. `다시`는 뜻 없는 말로 버리며 날짜 기준을 바꾸지 않는다.
- 미리보기에 `삭제 N개`와 지울 일정 목록을 강조해 보이고, 저장 전 확인창(`기존 일정 N개를 삭제합니다…`)을 한 번 더 띄운다. 삭제와 등록은 같은 트랜잭션이며 미리보기 이후 기존 일정이 바뀌면 409.
- 삭제 절은 문장 맨 앞에서만, 색 절은 `색`으로 끝나고 앞뒤가 띄어진 경우만 인식한다(`휴무는 빨간색`, `빨간색으로`). 제목 속 `삭제방지`, `빨간색연필`, `회의` 같은 글자는 명령으로 읽지 않는다.
- 지원하지 않는 예: `근무 일정을 삭제해줘`(제목별 삭제), `빨간색으로 삭제해줘`, `휴무는 빨강`(`색` 생략).

### 13.11 AI 보조 해석 (2026-10-20, 사용자 결정)

13.9의 외부 LLM 결정을 다음으로 확정했다: 공급자 Google Gemini API **무료 등급**, 모델 `gemini-3.5-flash-lite`(측정 평균 약 1초; `gemini-flash-latest`는 정확하나 평균 87초라 제외), 비용 0원.

- 순서: 규칙 파서(13.3·13.10) → 실패한 문장만 Gemini. 보내는 것은 문장뿐이다. 응답은 JSON 스키마(`supported`, `deleteScope: none|all|specific`, `fromToday`, `rule`)로 받고 규칙 파서와 같은 검증(일수 1~30, 제목 1~30자·일수/휴무 표현 금지, 색 6종)을 통과해야 한다.
- 삭제: **AI 경로에서는 삭제가 일어나지 않는다.** 문장 맨 앞에 삭제 절(`해당 기간/그날/모든/기존 + 일정·거 + 삭제·제거·지우기·날리기·비우기`)이 있으면 규칙 파서가 문장 전체를 읽은 경우에만 처리하고 AI로 보내지 않는다(`삭제하고 싶지 않고 …`처럼 뒷말을 모델이 놓쳐 전체 삭제되는 것을 막음). 삭제 절이 없는 문장만 AI로 가며, 모델이 그 안에서 삭제 요청을 보면(`deleteScope`가 `none`이 아니면) 거부한다. 규칙 파서는 일수로 `이틀~열흘` 한글 표현도 읽는다. 삭제 절은 등록이 이어지면 `삭제하고/삭제한 뒤/삭제 후/지우고`처럼 접속어까지, 삭제만이면 동사 뒤가 문장 끝이어야 인정한다. 그래서 `병원 일정 빼고 모든 일정 삭제`, `근무 일정은 제외하고 기존 일정 다 지워`, `근무 일정을 삭제해줘`는 거부되고, `모든 일정 삭제하지 말고/삭제 안 하고/삭제 말고 …`는 삭제가 되지 않는다.
- 화면 안내: 무료 등급에서는 Google이 입력·응답을 제품 개선에 쓰고 사람이 검토할 수 있음을 입력 전에 알리고 개인정보·민감정보를 넣지 말라고 안내한다(우리 서버는 저장하지 않음).
- 저장 단계는 모델을 다시 부르지 않는다. 미리보기 응답의 `commandToken`(같은 문장에 묶인 서버 서명)으로 같은 해석을 쓴다. 미리보기 화면에 `AI가 해석한 결과입니다. 아래 내용이 맞는지 확인해 주세요.`를 보인다.
- 실패: 키 없음·해석 불가 → 기존 미지원 문구(400). 429 → `지금은 문장 해석 요청이 많습니다. 1분쯤 뒤…`(503). 시간 초과(10초)·장애 → `지금은 문장을 해석할 수 없습니다…`(503). 어떤 경우에도 저장하지 않는다.
- 한계: 무료 등급 한도(분당 약 10회)는 모든 매장이 나눠 쓴다. 운영 전 유료 전환 또는 공급자 교체를 다시 결정한다.
