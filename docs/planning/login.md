# 로그인 기획서

상태: 결정 확정(2026-10-15). 구현 지시 전. 결정 내용은 끝의 '결정 사항' 절.

## 1. 목적

- **외부 공개 전 차단**: 지금은 주소만 알면 누구나 `POST /api/schedule`(요청당 CPU 최대 100초)를 쓸 수 있다. 로그인한 관리자만 화면과 API를 쓰게 한다.
- **나중을 막지 않기**: 근무표 저장(DB), 여러 매장, 직원 계정을 붙일 때 다시 만들지 않도록 계정에 `매장` 개념을 처음부터 둔다.
- 범위 밖: 근무표 저장, 직원용 화면, 결제, 셀프 가입(결정 사항 3).

## 2. 사용자와 권한

| 사용자 | 하는 일 | 권한 |
|---|---|---|
| 매장 관리자 | 로그인해 근무표를 만든다 | 화면 전체, `/api/schedule` |
| 운영 담당자(우리 팀) | 계정을 만들고, 비밀번호를 재설정하고, 잠금을 해제한다 | 서버 관리 도구(화면 없음) |
| 로그인하지 않은 방문자 | 로그인 화면만 본다 | 그 외 모든 페이지·API 거부 |

- 계정 1개 = 매장 1곳의 관리자 1명. 계정마다 `매장 이름`을 저장하고 헤더에 보여 준다.
- 화면 안의 권한 구분은 없다(관리자만 있음).

## 3. 사용자 흐름

```
첫 방문(/) ──로그인 안 됨──▶ 로그인(/login?next=/) ──성공──▶ 메인(/) 1 근무 조건 입력
                                   │실패 ──▶ 같은 화면 오류 문구
                                   │5회 실패 ──▶ 잠김(15분)
                                   └"비밀번호를 잊으셨나요?" ──▶ 안내 문구(운영 담당자 문의)
메인 헤더 [로그아웃] ──결과가 화면에 있으면 확인──▶ 로그인(/login), "로그아웃했습니다."
세션 만료 ──다음 요청 때 감지──▶ 입력 보관 ──▶ 로그인("다시 로그인해 주세요.") ──성공──▶ 메인, 입력 복원
```

1. **첫 방문**: 로그인 안 된 상태로 어떤 주소에 들어와도 `/login?next=<원래 주소>`로 보낸다. `next`는 같은 사이트 경로(`/`로 시작, `//` 아님)만 허용하고 아니면 `/`.
2. **로그인 성공**: `next`로 이동. 이미 로그인한 상태로 `/login`에 오면 바로 `/`.
3. **로그아웃**: 헤더 [로그아웃]. 화면에 결과 근무표가 있으면 먼저 확인 대화상자를 띄운다. 저장 기능이 없어서 로그아웃하면 근무표가 사라지기 때문이다.
4. **세션 만료**: 화면은 그대로 두고, 다음 서버 요청([근무표 만들기])이 401을 받으면
   - 지금 입력(JSON 텍스트)을 이 브라우저의 `sessionStorage`에 보관하고 로그인 화면으로 보낸다.
   - 다시 로그인하면 보관한 입력을 복원하고 지운다. 관리자가 30분 넘게 입력한 내용을 잃지 않게 하는 것이 핵심이다.
   - 결과 근무표는 보관하지 않는다(다시 만들면 된다).
5. **비밀번호 분실**: 셀프 재설정 없음(이메일 발송 수단이 없음). 링크를 누르면 로그인 카드 안에 안내 문구를 펼친다.
6. **계정 생성**: 운영 담당자가 서버 관리 도구(스크립트)로 만들고 아이디와 첫 비밀번호를 관리자에게 따로 전달한다. 화면에는 가입 메뉴가 없다.

## 4. 화면

UI 가이드(`docs/design/ui-guide.md`) 토큰과 컴포넌트를 그대로 쓴다. 새 컴포넌트는 없다.

### 4.1 로그인 (`/login`)

```
            교대근무 스케줄러
     근무 조건을 넣으면 근무표를 만들어 드립니다.
┌ 로그인 ───────────────────────────────┐
│ [안내 상자: 만료/로그아웃 문구 — 있을 때만]  │
│ 아이디(이메일)  [                    ]   │
│ 비밀번호        [                ] [보기] │
│ □ 로그인 상태 유지 (개인 기기에서만)        │
│ [오류 상자 — 있을 때만]                   │
│ [          로그인          ]  ← primary  │
│ 비밀번호를 잊으셨나요?                     │
└──────────────────────────────────────┘
```

- 가운데 카드 하나, 폭 최대 400px, 모바일은 좌우 16px. 헤더(sticky)는 없다.
- 아이디 입력: `type="email"`, `autocomplete="username"`, 자동 포커스. 비밀번호: `autocomplete="current-password"`, [보기]는 `.btn-secondary` 작은 버튼(`aria-pressed`). 브라우저 비밀번호 관리자가 동작해야 한다.
- Enter로 제출. 제출 후 비밀번호 칸만 비우고 아이디는 남긴다.

| 상태 | 화면 |
|---|---|
| 정상 | 위 배치, 버튼 활성 |
| 입력 누락 | 제출 시 해당 칸 `aria-invalid` + 칸 아래 문구 "아이디를 입력해 주세요." / "비밀번호를 입력해 주세요." 서버로 보내지 않음 |
| 로딩 | 버튼 안 스피너 + "로그인하는 중…", 버튼·입력 비활성, `aria-busy` |
| 실패 | `.alert-danger` `role="alert"`: "아이디 또는 비밀번호가 맞지 않습니다. 다시 확인해 주세요." |
| 잠김 | `.alert-warning`: "로그인을 여러 번 실패해 15분 동안 잠겼습니다. 잠시 뒤 다시 시도하거나 운영 담당자에게 문의해 주세요." 버튼은 활성 유지(시간이 지나면 바로 시도 가능) |
| 너무 잦은 요청(IP) | `.alert-warning`: "로그인 시도가 너무 많습니다. 잠시 뒤 다시 시도해 주세요." |
| 서버 오류·연결 실패 | `.alert-danger`: "로그인 중에 서버 문제가 생겼습니다. 잠시 뒤 다시 시도해 주세요." / 기존 연결 실패 문구 재사용 |
| 세션 만료로 옴 | `.alert-info`: "로그인 시간이 지나 다시 로그인해 주세요. 입력하던 근무 조건은 이 브라우저에 보관했습니다." |
| 로그아웃 후 | `.alert-info`: "로그아웃했습니다." |
| 비밀번호 분실 펼침 | `.alert-info`: "비밀번호는 운영 담당자가 다시 설정해 드립니다. 운영 담당자에게 아이디(이메일)를 알려 주세요." (연락처는 배포 시 정함) |

### 4.2 메인 헤더 변경 (`/`)

- 헤더 오른쪽 근무 기간 뒤에 `매장 이름` (muted 12px) + [로그아웃] `.btn-secondary` 작은 버튼. 모바일에서는 근무 기간 아래 줄로 내린다.
- 로그아웃 확인(결과가 있을 때만): "로그아웃하면 화면의 근무표가 사라집니다. 로그아웃할까요?" [취소] [로그아웃]. 네이티브 `<dialog>`, 포커스는 [취소]에 둔다.
- 입력 복원 직후 1 근무 조건 입력 위에 `.alert-info` 한 번: "로그인 전에 입력하던 근무 조건을 불러왔습니다."
- 복원 외 메인 화면은 바꾸지 않는다.

## 5. 정책

| 항목 | 규칙 |
|---|---|
| 아이디 | 이메일 주소. 저장·비교 전에 앞뒤 공백 제거 + 소문자. 최대 254자 |
| 비밀번호 | 10~64자, 문자 종류 조합 강제 없음. 아이디와 같으면 거부. 운영 담당자가 만들 때 적용(화면에서 바꾸는 기능은 이번 범위 밖) |
| 저장 | 비밀번호는 `scrypt`(Node 내장 `crypto`) + 계정별 salt 해시로만 저장. 평문·되돌릴 수 있는 암호화 금지 |
| 실패 횟수 | 같은 아이디로 15분 안에 5회 실패 → 15분 잠김. **없는 아이디에도 같은 카운터를 적용**해 잠김 문구로 계정 존재를 알 수 없게 한다. 성공하면 초기화 |
| IP 제한 | 같은 IP에서 1분에 20회 넘는 로그인 요청 → 429 |
| 계정 파일 | 서버의 JSON 파일(이메일, 매장 이름, scrypt 해시). Docker 배포 시 이미지 밖 볼륨에 둔다(컨테이너를 다시 만들어도 계정이 남게). 경로는 환경변수 |
| 세션 | 서명된 쿠키(`HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`). 서명 키는 환경변수, 코드·이미지에 넣지 않음 |
| 세션 유지 | 기본: 브라우저를 닫으면 끝, 마지막 사용 후 2시간이 지나면 만료. '로그인 상태 유지' 체크: 14일. 둘 다 로그인부터 최대 14일 |
| 로그아웃 | 쿠키 삭제. 모든 기기 일괄 로그아웃은 서명 키 교체(운영 작업)로 대신한다 |
| 보호 범위 | `/login`과 정적 파일을 뺀 모든 페이지와 API. API는 로그인 안 되면 리다이렉트 대신 401 JSON |
| 오류 문구 | 아이디가 없는지, 비밀번호가 틀렸는지 구분하지 않는다. 응답 시간도 비슷하게(없는 아이디도 해시 계산) |
| 엔진 사용량 | 기존 동시 실행 제한(`ENGINE_MAX_CONCURRENCY`) 유지. 계정별 제한은 이번 범위 밖(셀프 가입을 열 때 다시 판단) |

## 6. 보안·개인정보 최소 요구

- 외부 공개는 HTTPS에서만. `Secure` 쿠키 때문에 HTTP에서는 로그인이 되지 않는다(로컬 개발은 예외 처리).
- 로그인 POST는 CSRF 방지: `SameSite=Lax` + `Origin` 헤더가 우리 사이트인지 확인.
- 로그에 비밀번호·쿠키·서명 키를 남기지 않는다. 실패 로그에는 시각, IP, 아이디(이메일)만 남긴다.
- 개인정보: 저장하는 것은 관리자 이메일, 매장 이름, 비밀번호 해시뿐이다. 근무표의 직원 이름은 지금처럼 서버에 저장하지 않는다(요청 처리 뒤 임시 파일 삭제). 공개 전에 개인정보 처리방침에 이 세 항목과 보관 기간(계정 삭제 시 즉시 삭제)을 적는다.
- `/login` 응답에 `Cache-Control: no-store`.

## 7. 완료 기준

1. 로그인하지 않은 상태에서 `/`는 `/login?next=/`로, `POST /api/schedule`은 401로 막힌다(curl로 확인).
2. 올바른 아이디·비밀번호로 로그인하면 메인으로 가고 근무표를 만들 수 있다.
3. 틀린 비밀번호와 없는 아이디의 오류 문구, 상태 코드, 잠김 동작이 같다.
4. 5회 실패하면 15분 동안 맞는 비밀번호로도 로그인되지 않는다.
5. '로그인 상태 유지'를 안 하면 브라우저를 다시 열었을 때 로그인 화면이 나오고, 하면 그대로 들어간다.
6. 입력 중 세션이 만료된 뒤 [근무표 만들기] → 로그인 → 입력이 그대로 복원된다.
7. 결과가 있을 때 로그아웃하면 확인 대화상자가 뜬다.
8. 쿠키에 `HttpOnly`·`Secure`·`SameSite=Lax`가 붙고, 저장소에 평문 비밀번호가 없다.
9. 로그인 화면이 키보드만으로 동작하고, 라이트·다크 모두 UI 가이드의 대비 기준을 지킨다.
10. 운영 담당자가 문서화된 명령 하나로 계정 생성·비밀번호 재설정·잠금 해제를 할 수 있다.

## 8. 결정 사항

2026-10-15 사용자 확정(dev-lead 경유). 모두 추천안 A.

| 항목 | 결정 | 고르지 않은 안 |
|---|---|---|
| 1. 계정 모델 | 계정 1개 = 매장 1곳 = 관리자 1명 | 조직·여러 매장·여러 관리자(근무표 저장과 함께 다시 검토) |
| 2. 인증 방식 | 아이디(이메일)·비밀번호 | 매직링크, 소셜(셀프 가입을 열 때 카카오 재검토), 사내 SSO |
| 3. 가입 방식 | 운영 담당자가 생성 | 셀프 가입, 초대 |
| 4. 직원 계정 | 이번 범위에서 제외 | 직원 근무표 보기(근무표 저장 DB 선행) |
| 5. 계정 저장소 | 서버의 계정 파일(JSON, scrypt 해시) + 운영 스크립트 | 지금 DB 도입(근무표 저장·배포 호스트 결정 때 함께 검토) |
| 세션 유지 기간 | 5절 값 그대로(기본 2시간 무활동 만료, '로그인 상태 유지' 14일) | — |

DB로 옮기는 시점: 계정이 수십 개를 넘거나 근무표 저장을 시작할 때.
