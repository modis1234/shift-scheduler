# 캘린더 저장·게시 백엔드 검토

## 결론

수정 후 통과 권고. 매장별 접근은 세션의 store id로 제한되고 게시 교체는 트랜잭션 및 부분 UNIQUE 인덱스로 처리된다. 다만 DB 파일 권한과 근무 기간 입력 검증에 각각 개인정보·데이터 무결성 결함이 있다.

## 발견 사항

- **MEDIUM — 기존 SQLite 파일의 권한을 0600으로 강제하지 않음** — `web-client/src/lib/schedules.ts:23`. `openSync(file, "a", 0o600)`의 mode는 파일을 새로 만들 때만 적용하고 이미 있는 파일의 권한은 바꾸지 않는다. 재현: 기존 파일을 `chmod 0644` 한 뒤 해당 방식으로 열어도 mode가 `0644`로 남는다(검토용 `/tmp` 재현). schedules DB에는 직원 이름·휴가와 입력/결과 데이터가 저장되므로, 운영자가 사전 생성·복구·이관한 DB가 group/world-readable이면 서비스 계정 외 로컬 사용자가 개인정보를 읽을 수 있다. 기존 파일에도 권한을 강제하거나 부적절한 권한이면 시작을 거부해야 한다.
- **MEDIUM — 저장 API가 달력상 불가능한 날짜와 엔진 허용 기간 초과를 저장** — `web-client/src/app/api/schedules/route.ts:7,40`. 정규식은 `YYYY-MM-DD` 모양만 확인하고 실제 날짜 유효성 및 최대 366일을 확인하지 않는다. `start_date=end_date="2026-02-31"`은 정규식과 순서 검사를 통과해 `{status:"SUCCESS", schedules:[]}`와 함께 저장된다. `2026-01-01`~`2027-01-02`(367일)도 같은 경로로 통과한다. 프런트의 `formatDate`는 불가능한 날짜를 원문 그대로 표시하므로 잘못된 기간 레코드가 목록에 남고, 정상 엔진이 만들 수 없는 입력/결과 쌍을 저장할 수 있다. 서버에서 실제 YYYY-MM-DD 유효성과 366일 상한을 검증해야 한다.

## 요청된 검토 항목

- 매장 격리: 목록/조회/삭제/게시/게시 취소 모두 요청 세션의 store id에 한정되며, 타 매장 id는 404다. `publishSchedule`의 최종 UPDATE(`schedules.ts:85`)에는 store 조건이 없지만 같은 `BEGIN IMMEDIATE` 트랜잭션 내에서 직전 SELECT가 `store_id = ? AND id = ?`로 대상을 확인하고 `id`가 전역 PK이므로 현재 구현에서 타 매장 row를 갱신하는 경로는 확인하지 못했다. 방어적 일관성을 위해 UPDATE에도 store 조건을 넣을 수 있으나, 이번 검토에서는 실제 교차 매장 결함으로 분류하지 않았다.
- 게시 교체: 이전 게시 취소와 새 게시를 `BEGIN IMMEDIATE` 안에서 처리하고 오류 시 rollback한다. 같은 매장·같은 기간의 게시 1개는 부분 UNIQUE 인덱스로 보강된다.
- 본문 제한/필수 형식: stream 기준 1 MiB 제한, JSON 객체, `SUCCESS`, schedules 배열을 확인한다. 경계 테스트가 1 MiB 초과 413을 확인했다.
- 클라이언트 result의 엔진 재검증: 현재 관리자 전용 저장 단계에서 직접 수정 UI가 없고, 세션 매장 밖으로 결과가 제공되지 않아 이 범위의 미재검증 판단은 수용 가능하다. 직원 공유/외부 응답을 추가할 때는 이 전제에 의존하지 말고 서버 측 검증과 개인정보 필터를 적용해야 한다.
- 개인정보 로그: 저장 API 및 저장소 코드에서 input/result 본문을 로그로 남기는 호출은 확인하지 못했다.
- SCHEDULES_DB: 기본값 없이 요구하고 경로를 명시적으로 받는다. 새 DB 생성 mode는 0600이나 기존 파일 mode 미강제가 위 finding이다.

## 검증

- `npm run lint --prefix web-client`: 통과.
- 제공된 scratchpad 전용 `rerun.sh` 실행: 로그인 58/58, 저장·게시 30/30 통과. 공유 web-client의 build/dev는 실행하지 않았다.
- 날짜 predicate 재현: `2026-02-31`은 서버 정규식과 문자열 순서 검사를 통과하고 JS 날짜로 정규화하면 `2026-03-03`이 됨.
- 파일 권한 재현은 `/tmp`에서 수행: 기존 mode 0644 파일을 `openSync(path, "a", 0o600)`로 열어도 0644 유지.
